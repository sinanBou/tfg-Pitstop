========================================================================
PATRONES DE DISEÑO APLICADOS - PITSTOP PARTS & INVENTORY REFACTOR
========================================================================

En esta refactorización integral del sistema de repuestos y control de almacén, se han integrado y documentado de forma activa cuatro patrones de diseño de la banda de los cuatro (GoF):

1. BUILDER PATTERN (Creación)
-----------------------------
- Cómo se creó: Se aplicó la anotación Lombok `@Builder` en todas las nuevas entidades JPA (`PartCatalog`, `WorkshopInventory`, `AppointmentPart`) y sus DTOs correspondientes.
- Propósito: Facilita la creación fluida y segura de objetos del dominio complejos evitando constructores monolíticos cargados de parámetros difíciles de seguir y controlando la inmutabilidad de los datos.

2. STRATEGY PATTERN (Comportamiento)
-----------------------------------
- Cómo se creó: 
  - Se definió la interfaz común `PartPricingStrategy` con el método `double calculatePrice(double baseRetailPrice);`.
  - Se crearon las clases concretas de estrategia:
    - `StandardPricingStrategy`: Aplica el precio de venta sugerido original del inventario.
    - `DiscountPricingStrategy`: Permite fijar un descuento variable (ej. 10% promocional) al precio del repuesto al asignarlo a la cita.
- Propósito: Desacopla la lógica comercial de facturación y cálculo de precios del repuesto. La capa de servicio puede recibir dinámicamente cualquier estrategia en el futuro sin modificar la lógica principal.

3. OBSERVER PATTERN (Comportamiento)
-----------------------------------
- Cómo se creó: 
  - Se creó el evento Spring `LowStockEvent` que transporta los detalles del stock mínimo.
  - Se implementó el observador `InventoryStockObserver` anotado con `@Component` que escucha estos eventos mediante `@EventListener`.
  - En `PartService.java`, cuando las existencias descienden por debajo de `avisoThreshold`, el publicador de eventos de Spring despacha el evento.
- Propósito: Permite que el control de stock notifique alarmas de forma asíncrona y totalmente desacoplada del hilo de guardado transaccional principal, facilitando la futura adición de pasarelas de email o SMS.

4. FACADE PATTERN (Estructura)
------------------------------
- Cómo se creó: Se implementó la clase `PartInventoryFacade` para encapsular las llamadas cruzadas complejas del servicio de piezas (descontar stock, disparar observadores, instanciar estrategias de precios, calcular costes).
- Propósito: Ofrece una interfaz unificada y ultra-simplificada para el controlador de la API (`PartController`), de modo que éste no requiera conocer las interioridades transaccionales complejas de la gestión de existencias y facturación.

5. REPOSITORY PATTERN (Estructura)
----------------------------------
- Cómo se creó: Se crearon las interfaces `PartCategoryRepository` y `PartCatalogRepository` extendiendo `JpaRepository<T, UUID>`.
- Propósito: Aísla la capa del dominio y la lógica de negocio pura de la infraestructura física de acceso a datos (base de datos relacional H2/PostgreSQL). Permite realizar consultas seguras, tipos fuertemente tipados y operaciones CRUD atómicas sin escribir SQL manual o acoplar la base de datos a los servicios.

6. BUILDER PATTERN (Creación) - Extensión PartCategory
------------------------------------------------------
- Cómo se creó: Se aplicó la anotación Lombok `@Builder` en la nueva entidad relacional `PartCategory`.
- Propósito: Permite instanciar de forma fluida y clara las nuevas categorías con sus slugs dinámicos e inicializar colecciones internas de forma inmutable a través de `@Builder.Default`.

7. ADAPTER PATTERN (Estructura) - SettingsTab Dual-Mode
--------------------------------------------------------
- Cómo se creó: Se refactorizó `SettingsTab.tsx` para soportar múltiples modos de renderizado mediante props condicionales (`readOnlyWorkshop`, `showProfileSection`).
  - Modo Owner/Manager: Formulario editable de taller + sección de edición de perfil personal.
  - Modo Mecánico: Vista de solo lectura de la configuración del taller (sin perfil).
- Backend: Se creó `PUT /api/employees/me` con `UpdateProfileRequest` que solo permite campos seguros (nombre, apellido, dirección).
- Propósito: Un único componente se adapta a diferentes roles y contextos de usuario sin duplicación de código, respetando el principio de responsabilidad única y la seguridad por diseño.

8. CAPABILITY / DYNAMIC TAB AUTHORIZATION PATTERN (Comportamiento)
-----------------------------------------------------------------
- Cómo se creó:
  - En la entidad `Employee`, se introdujo un campo de texto `allowedSections` que persiste los permisos granulares concedidos.
  - En el controlador `EmployeeController`, se expuso el endpoint seguro `PUT /api/employees/{id}/allowed-sections` para gestionar estos accesos desde la interfaz de ajustes de Owners/Managers.
  - En el frontend, el panel de mecánicos `WorkerDashboard.tsx` lee las capacidades dinámicamente y computa la barra de navegación `SECCIONES` basándose en este claim.
- Propósito: Desacopla los menús e interfaces del rol estático tradicional, permitiendo una asignación fluida y granular de responsabilidades a nivel de base de datos que se refleja de inmediato en caliente en el cliente sin requerir relogueo completo.

9. STRATEGY PATTERN & DEPENDENCY INVERSION PRINCIPLE (DIP) - Storage Provider
-----------------------------------------------------------------------------
- Cómo se creó:
  - Se creó la interfaz de desacoplamiento `StorageService` con métodos estandarizados para subir y eliminar archivos (`uploadFile`, `deleteFile`).
  - Se implementó de forma modular la clase concreta `S3StorageService` conectada a un cliente `S3Client` de AWS SDK v2, cuyas credenciales seguras e inyecciones dinámicas se resuelven en la clase de configuración `S3Config` mediante properties.
- Propósito: Sigue estrictamente la inversión de dependencias (DIP) del Clean Code. La capa de negocio interactúa únicamente con la abstracción `StorageService`, lo que permite que el taller pueda migrar en caliente de AWS S3 a Azure Blob Storage, Google Cloud Storage, o almacenamiento local en desarrollo con tan solo inyectar una clase alternativa sin romper ni modificar una sola línea de código en los servicios o controladores.

10. PORTAL MODAL PATTERN (Estructura) - MiPerfil & PerfilTaller
-----------------------------------------------------------------
- Cómo se creó:
  - Se extrajeron los modales inline de "Mi Perfil" y "Perfil del Taller" desde `WorkshopAdminDashboard.tsx` y `WorkerDashboard.tsx` a componentes independientes: `MiPerfil.tsx` y `PerfilTaller.tsx`.
  - Ambos componentes utilizan `ReactDOM.createPortal(…, document.body)` para renderizarse fuera del stacking context del DOM padre, resolviendo el bug del botón X que no respondía al estar atrapado dentro de un contenedor `overflow-y-auto` con `z-index` relativo.
  - El botón de cierre se posiciona `absolute` sobre el contenedor modal principal (fuera del scroll wrapper), garantizando que siempre sea accesible y clicable independientemente del scroll.
  - `MiPerfil` internaliza su propio estado local (`uploadingAvatar`, `profileSaved`, `fileInputRef`) reduciendo la complejidad del componente padre.
- Propósito: Aplica el principio de responsabilidad única (SRP) extrayendo la lógica de UI modal a componentes reutilizables, y utiliza portales de React para evitar conflictos de stacking context en modales con scroll.

Elimina la duplicación de código en la visualización de KPIs financieros, homogeneiza la estética seria/corporativa del ecosistema y permite que todos los componentes analíticos reaccionen al mes seleccionado de forma independiente y aislada.

14. GATEKEEPER PATTERN - VEHICLE RECEPTION GUARD (Comportamiento / Seguridad)
------------------------------------------------------------------------------
- Cómo se creó:
  - Backend: Se añadió el campo `vehicleReceived` al DTO `WorkshopTaskDTO` y se mapeó en `WorkshopTaskService.convertToDTO()` leyendo el estado de la cita origen (`originAppointment.getVehicleReceived()`). Las citas (`AppointmentDTO`) ya exponían este campo.
  - Frontend: Se implementó una cláusula guard `isVehicleReceived = appointment.vehicleReceived !== false` en los componentes `AppointmentBlock.tsx` y `MechanicLiveTask.tsx`.
  - Cuando `vehicleReceived === false`:
    - Los botones de "Gestionar" y "Checklist" se deshabilitan visualmente con estilo amber y muestran un icono de candado.
    - Los botones de transición de estado (Confirmar, Iniciar Trabajo, Finalizar) se bloquean con texto "Recepción Pendiente".
    - Se muestra un banner informativo "Pendiente de Recepción" en el componente `MechanicLiveTask`.
- Propósito: Fuerza el cumplimiento del procedimiento operativo estándar del taller: ningún trabajo puede iniciarse ni gestionarse hasta que el vehículo haya sido físicamente recibido e inspeccionado. Protege contra errores humanos de planificación y garantiza la integridad del flujo administrativo.

---------------------------------------------------------------------------------------------------------
- Cómo se creó:
  - Se identificó que la clase monolítica original `EmployeService` contenía dos dominios de negocio diferenciados: el control de los datos del perfil propio de un empleado (Self Profile CRUD) y la administración de los empleados del taller por parte de un administrador (Team Administration).
  - Se dividió este servicio en dos clases de alta cohesión: `EmployeeProfileService` (encargada estricta de `/me`, `/me/avatar`) y `EmployeeAdminService` (encargada de listados de equipo, registros, despidos, ascensos/descensos de gerencia y permisos).

  - Se adaptó `EmployeeController` para inyectar ambos servicios especializados de forma limpia, y se eliminó por completo el archivo legado duplicado.
- Propósito: Sigue rigurosamente el principio de responsabilidad única (SRP). Evita que los cambios operativos sobre la gestión de personal (Team Administration) afecten al flujo de modificación de datos personales (Profile CRUD) o viceversa. Aumenta la mantenibilidad y facilita la creación de pruebas unitarias específicas de alta granularidad.

- Propósito: Sigue estrictamente el principio de responsabilidad única (SRP) y Open/Closed (OCP), aislando la lógica de negocio y transición de citas de la lógica de consulta y visualización de facturas, eliminando la duplicación y cuellos de botella de rendimiento de consultas recurrentes (N+1 database query issues).

24. SINGLE RESPONSIBILITY SERVICE SEPARATION PATTERN (Estructura / Clean Architecture) - Módulo de Repuestos (Parts)
-------------------------------------------------------------------------------------------------------------------
- Cómo se creó:
  - Se identificó que la clase monolítica original `PartService` contenía múltiples dominios de negocio diferenciados: la administración de categorías y de piezas en el inventario (Part Category Creation/Deletion, Inventory stock addition/updates/deletions), las consultas de búsqueda y lectura (Part Catalog Lists, Inventory Stock lists, Appointment parts lookup, Category Lists), y la lógica compleja de asignación/desasignación de piezas (applying dynamic Pricing Strategies, triggering low stock Observer events, decrementing/restoring stocks, recalculating labor and parts cost totals).
  - Se dividió este servicio en tres clases independientes y altamente cohesivas dentro del subpaquete `org.tfg.backend.part.service`:
    * `PartAdminService`: Encargada de altas/modificaciones/bajas de almacén e inventario, inicializaciones de catálogos y gestión de categorías.

    * `PartAssignmentService`: Encargada de las lógicas transaccionales complejas de asignación de piezas estándar (con patrones Observer/Strategy), asignación de piezas personalizadas con precio pendiente, desasignación de repuestos y recalculo de totales de cita.
  - Se refactorizó `PartController` y `PartInventoryFacade` para inyectar estos servicios independientes y se eliminó por completo el archivo monolítico legado redundante.
- Propósito: Sigue estrictamente el principio de responsabilidad única (SRP) y Open/Closed (OCP), aislando la lógica operacional de mutación de stocks del taller del comportamiento y lógica transaccional de asignación a citas por parte del mecánico y de las consultas rápidas de lectura, aumentando notablemente la granularidad de los tests y la robustez global ante picos de demanda.

-------------------------------------------------------------------------------------------------------------------
- Cómo se creó:

- Propósito: Aísla la lógica de negocio y consulta de datos del comportamiento de representación y transformación de datos, permitiendo una suite de tests unitarios aislada con un 100% de éxito, y reduce la duplicación de código en la capa de controladores y servicios de autenticación.

-------------------------------------------------------------------------------------------------------------------
- Cómo se creó:
  - Se identificó que la clase monolítica original `CatalogService` combinaba las operaciones de mutación y administración (crear categorías, autogenerar códigos secuenciales a través de prefijos numéricos o hashes ligeros de nombres, crear tareas, actualizar especificaciones y horas, y eliminación de tareas) con la consulta de solo lectura de categorías asociadas a talleres.
  - Se dividió esta clase en subpaquetes y componentes altamente cohesivos:
    * `CatalogAdminService`: En la carpeta `org.tfg.backend.taskcatalog.service`, gestiona de manera aislada la lógica de mutación de catálogo, inicialización y autogeneración de códigos secuenciales para tareas.
    * `CatalogLookupService`: En la carpeta `org.tfg.backend.taskcatalog.service`, gestiona exclusivamente las consultas de lectura ordenadas de categorías y tareas para talleres.
  - Se actualizó `CatalogController` para inyectar y delegar llamadas a estos dos servicios independientes y se eliminó por completo el archivo monolítico legado redundante.
- Propósito: Sigue estrictamente el principio de responsabilidad única (SRP), previniendo que los rápidos flujos de consulta de catálogos y tareas de la app web por mecánicos y clientes sufran degradaciones por bloqueos de transacciones de mutación o reajuste de tareas complejas, mejorando drásticamente el aislamiento y la modularidad en los tests del backend.


27. SINGLE RESPONSIBILITY SERVICE SEPARATION PATTERN (Estructura / Clean Architecture) - Módulo de Tareas del Taller (Workshop Tasks)
-------------------------------------------------------------------------------------------------------------------
- Cómo se creó:
  - Se identificó que la clase monolítica original `WorkshopTaskService` combinaba las operaciones de mutación y asignación del personal (actualizaciones de tareas, reasignaciones de empleados, lógicas transaccionales y condicionales complejas de borrado de tareas contra citas asociadas reduciendo el estado a `CANCELLED` si la cita tiene múltiples tareas o desvinculando la cita para dejarla sin asignar si era la única) con consultas rápidas de lectura (búsqueda de tareas por rango de fechas por taller y por empleado).
  - Se dividió esta clase en subpaquetes y componentes altamente cohesivos:
    * `WorkshopTaskMapper`: En la carpeta `org.tfg.backend.workshoptask.mapper`, se encarga de manera aislada de la transformación de entidades `WorkshopTask` a `WorkshopTaskDTO` formateando campos descriptivos de vehículo, taller, empleado y cliente.
    * `WorkshopTaskAdminService`: En la carpeta `org.tfg.backend.workshoptask.service`, gestiona de manera aislada las operaciones de modificación de estado, reasignaciones condicionales de mecánicos, cancelaciones y eliminaciones lógicas de tareas.
    * `WorkshopTaskLookupService`: En la carpeta `org.tfg.backend.workshoptask.service`, gestiona de manera aislada la recuperación de tareas por fechas agrupadas por taller y mecánicos.
  - Se actualizó `WorkshopTaskController` para inyectar y delegar llamadas a estos servicios independientes y se eliminó por completo el archivo monolítico legado redundante.
- Propósito: Sigue estrictamente el principio de responsabilidad única (SRP), previniendo que la lógica de reasignación y el guardado de perfiles de la cita impacten en la velocidad y el rendimiento del listado y renderizado del calendario de tareas en la aplicación web, facilitando un mantenimiento totalmente desacoplado.


28. SPECIALIZED DATA TRANSFER OBJECT PATTERN (DTO Specialization) - Módulo de Registro
-------------------------------------------------------------------------------------
- Cómo se creó:
  - Se eliminó el DTO monolítico genérico `RegisterRequest` que acumulaba campos opcionales para roles dispares (como `nif`, `cif`, `companyName`, `address`, `phoneNumber`).
  - Se crearon DTOs específicos y fuertemente tipados: `ClientRegisterRequest` (para clientes independientes) y `OwnerRegisterRequest` (para gerentes/propietarios de talleres).
  - Se adaptaron los endpoints del controlador `/api/auth/register/client` y `/api/auth/register/workshop` para recibir sus DTOs correspondientes con validaciones `@Valid` estrictas e independientes.
- Propósito: Sigue los principios de robustez y Security-First del Clean Code. Evita el uso de campos nulos ambiguos, mejora la claridad y auto-documentación de la API de registro, e impide que un cliente registre de forma fraudulenta campos exclusivos de administradores de taller o viceversa.
