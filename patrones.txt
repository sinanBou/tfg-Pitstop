========================================================================
PATRONES DE DISEÑO APLICADOS - PITSTOP PARTS & INVENTORY REFACTOR
========================================================================

En esta refactorización integral del sistema de repuestos y control de almacén, se han integrado y documentado de forma activa cuatro patrones de diseño de la banda de los cuatro (GoF):

1. BUILDER PATTERN (Creación)
-----------------------------
- Cómo se creó: Se aplicó la anotación Lombok `@Builder` en todas las nuevas entidades JPA (`PartCatalog`, `WorkshopInventory`, `AppointmentPart`) y sus DTOs correspondientes.
- Propósito: Facilita la creación fluida y segura de objetos del dominio complejos evitando constructores monolíticos cargados de parámetros difíciles de seguir y controlando la inmutabilidad de los datos.

2. STRATEGY PATTERN (Comportamiento)
-----------------------------------
- Cómo se creó: 
  - Se definió la interfaz común `PartPricingStrategy` con el método `double calculatePrice(double baseRetailPrice);`.
  - Se crearon las clases concretas de estrategia:
    - `StandardPricingStrategy`: Aplica el precio de venta sugerido original del inventario.
    - `DiscountPricingStrategy`: Permite fijar un descuento variable (ej. 10% promocional) al precio del repuesto al asignarlo a la cita.
- Propósito: Desacopla la lógica comercial de facturación y cálculo de precios del repuesto. La capa de servicio puede recibir dinámicamente cualquier estrategia en el futuro sin modificar la lógica principal.

3. OBSERVER PATTERN (Comportamiento)
-----------------------------------
- Cómo se creó: 
  - Se creó el evento Spring `LowStockEvent` que transporta los detalles del stock mínimo.
  - Se implementó el observador `InventoryStockObserver` anotado con `@Component` que escucha estos eventos mediante `@EventListener`.
  - En `PartService.java`, cuando las existencias descienden por debajo de `avisoThreshold`, el publicador de eventos de Spring despacha el evento.
- Propósito: Permite que el control de stock notifique alarmas de forma asíncrona y totalmente desacoplada del hilo de guardado transaccional principal, facilitando la futura adición de pasarelas de email o SMS.

4. FACADE PATTERN (Estructura)
------------------------------
- Cómo se creó: Se implementó la clase `PartInventoryFacade` para encapsular las llamadas cruzadas complejas del servicio de piezas (descontar stock, disparar observadores, instanciar estrategias de precios, calcular costes).
- Propósito: Ofrece una interfaz unificada y ultra-simplificada para el controlador de la API (`PartController`), de modo que éste no requiera conocer las interioridades transaccionales complejas de la gestión de existencias y facturación.

5. REPOSITORY PATTERN (Estructura)
----------------------------------
- Cómo se creó: Se crearon las interfaces `PartCategoryRepository` y `PartCatalogRepository` extendiendo `JpaRepository<T, UUID>`.
- Propósito: Aísla la capa del dominio y la lógica de negocio pura de la infraestructura física de acceso a datos (base de datos relacional H2/PostgreSQL). Permite realizar consultas seguras, tipos fuertemente tipados y operaciones CRUD atómicas sin escribir SQL manual o acoplar la base de datos a los servicios.

6. BUILDER PATTERN (Creación) - Extensión PartCategory
------------------------------------------------------
- Cómo se creó: Se aplicó la anotación Lombok `@Builder` en la nueva entidad relacional `PartCategory`.
- Propósito: Permite instanciar de forma fluida y clara las nuevas categorías con sus slugs dinámicos e inicializar colecciones internas de forma inmutable a través de `@Builder.Default`.

7. ADAPTER PATTERN (Estructura) - SettingsTab Dual-Mode
--------------------------------------------------------
- Cómo se creó: Se refactorizó `SettingsTab.tsx` para soportar múltiples modos de renderizado mediante props condicionales (`readOnlyWorkshop`, `showProfileSection`).
  - Modo Owner/Manager: Formulario editable de taller + sección de edición de perfil personal.
  - Modo Mecánico: Vista de solo lectura de la configuración del taller (sin perfil).
- Backend: Se creó `PUT /api/employees/me` con `UpdateProfileRequest` que solo permite campos seguros (nombre, apellido, dirección).
- Propósito: Un único componente se adapta a diferentes roles y contextos de usuario sin duplicación de código, respetando el principio de responsabilidad única y la seguridad por diseño.

8. CAPABILITY / DYNAMIC TAB AUTHORIZATION PATTERN (Comportamiento)
-----------------------------------------------------------------
- Cómo se creó:
  - En la entidad `Employee`, se introdujo un campo de texto `allowedSections` que persiste los permisos granulares concedidos.
  - En el controlador `EmployeeController`, se expuso el endpoint seguro `PUT /api/employees/{id}/allowed-sections` para gestionar estos accesos desde la interfaz de ajustes de Owners/Managers.
  - En el frontend, el panel de mecánicos `WorkerDashboard.tsx` lee las capacidades dinámicamente y computa la barra de navegación `SECCIONES` basándose en este claim.
- Propósito: Desacopla los menús e interfaces del rol estático tradicional, permitiendo una asignación fluida y granular de responsabilidades a nivel de base de datos que se refleja de inmediato en caliente en el cliente sin requerir relogueo completo.

9. STRATEGY PATTERN & DEPENDENCY INVERSION PRINCIPLE (DIP) - Storage Provider
-----------------------------------------------------------------------------
- Cómo se creó:
  - Se creó la interfaz de desacoplamiento `StorageService` con métodos estandarizados para subir y eliminar archivos (`uploadFile`, `deleteFile`).
  - Se implementó de forma modular la clase concreta `S3StorageService` conectada a un cliente `S3Client` de AWS SDK v2, cuyas credenciales seguras e inyecciones dinámicas se resuelven en la clase de configuración `S3Config` mediante properties.
- Propósito: Sigue estrictamente la inversión de dependencias (DIP) del Clean Code. La capa de negocio interactúa únicamente con la abstracción `StorageService`, lo que permite que el taller pueda migrar en caliente de AWS S3 a Azure Blob Storage, Google Cloud Storage, o almacenamiento local en desarrollo con tan solo inyectar una clase alternativa sin romper ni modificar una sola línea de código en los servicios o controladores.

10. PORTAL MODAL PATTERN (Estructura) - MiPerfil & PerfilTaller
-----------------------------------------------------------------
- Cómo se creó:
  - Se extrajeron los modales inline de "Mi Perfil" y "Perfil del Taller" desde `WorkshopAdminDashboard.tsx` y `WorkerDashboard.tsx` a componentes independientes: `MiPerfil.tsx` y `PerfilTaller.tsx`.
  - Ambos componentes utilizan `ReactDOM.createPortal(…, document.body)` para renderizarse fuera del stacking context del DOM padre, resolviendo el bug del botón X que no respondía al estar atrapado dentro de un contenedor `overflow-y-auto` con `z-index` relativo.
  - El botón de cierre se posiciona `absolute` sobre el contenedor modal principal (fuera del scroll wrapper), garantizando que siempre sea accesible y clicable independientemente del scroll.
  - `MiPerfil` internaliza su propio estado local (`uploadingAvatar`, `profileSaved`, `fileInputRef`) reduciendo la complejidad del componente padre.
- Propósito: Aplica el principio de responsabilidad única (SRP) extrayendo la lógica de UI modal a componentes reutilizables, y utiliza portales de React para evitar conflictos de stacking context en modales con scroll.
